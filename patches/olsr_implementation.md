# Реализация атак на OLSR в NS-3.49

Патчи относятся к исходникам официального выпуска NS-3.49 и меняют только
`src/olsr/model/olsr-routing-protocol.cc` и
`src/olsr/model/olsr-routing-protocol.h`. Каждый патч применяется отдельно к
чистой версии; четыре патча нельзя накладывать последовательно на одно дерево.
Для каждой проверки создаётся отдельная рабочая копия NS-3.49.

## Основание реализации

Использованы исходные документация `src/olsr/doc/olsr.rst`, RFC 3626 и функции
штатного протокола NS-3.49: `RecvOlsr`, `ForwardDefault`, `SendHello`,
`SendTc`, `RouteInput`, `AssignStreams`. Схемы в
`materials/schemes/attacks/olsr_*_ru.png` задают механизм атак. Готовые
репутационные расширения и новые типы OLSR-сообщений не копировались.

## Чёрная дыра

Файл: `ns3-49-olsr-blackhole.patch`.

Параметры объекта `ns3::olsr::RoutingProtocol`:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `AttackEnabled` | `false` | Включает атаку только на выбранном узле |
| `AttackStart` | `0 s` | Момент начала подавления пересылки |

В `SendHello` включённый нарушитель объявляет `Willingness::ALWAYS`.
Это подготовка привлечения трафика, поэтому она действует и до `AttackStart`.
Высокая готовность не гарантирует центрального положения: результат зависит от
топологии и штатного выбора MPR.

В `ForwardDefault` отбрасываются только сообщения, которые узел действительно
должен был переслать: отправитель является симметричным соседом и селектором
MPR, сообщение не было переслано ранее, TTL больше единицы. Собственные
HELLO/TC и обработка принятых сообщений продолжаются. Подавленное сообщение
отмечается в Duplicate Set как уже рассмотренное для пересылки, чтобы его
повторная копия не получила второй шанс.

В `RouteInput` ветка атаки расположена после проверки собственных и локально
адресованных пакетов, перед транзитной пересылкой. Намеренно отброшенный пакет
считается обработанным (`return true`): `Ipv4ListRouting` не может передать его
другому маршрутизатору. ICMP-ошибка не генерируется, что соответствует скрытому
отбрасыванию. Событие доступно через trace source `AttackDrop` и
`GetAttackDataDrops()`. Отдельно считается `GetAttackControlDrops()`.

## Серая дыра

Файл: `ns3-49-olsr-grayhole.patch`.

Сохраняются точки вмешательства и параметры чёрной дыры. Дополнительно
`AttackDropProbability` задаёт вероятность независимого отбрасывания каждого
подходящего транзитного пакета или служебного сообщения, диапазон `[0, 1]`,
по умолчанию `0.5`. При `p=0` пересылка сохраняется; при `p=1` получается
чёрная дыра. Максимальная готовность в HELLO сохраняется при любом `p`, пока
`AttackEnabled=true`.

Вероятностное решение использует отдельный `UniformRandomVariable`.
При отключённой атаке этот объект не создаётся, поэтому штатные генераторы
сохраняют номера автоматически назначаемых потоков. `AssignStreams` задаёт
отдельный поток включённому нарушителю. Без явного назначения генератор
создаётся при первом вероятностном решении. При `p=0` и `p=1` решение
принимается без случайной выборки. Сначала задаются атрибуты, затем вызывается
`OlsrHelper::AssignStreams`. При неизменных seed, run и потоках запуск
воспроизводим. Число потерь в конечной выборке зависит от случайных значений.

## Сивилла

Файл: `ns3-49-olsr-sybil.patch`.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `SybilEnabled` | `false` | Включить несколько личностей одного физического узла |
| `SybilCount` | `3` | Число поддельных адресов, от 1 до 64 |
| `SybilAddressBase` | `10.254.0.1` | Первый адрес зарезервированного непрерывного диапазона |

При каждом `SendHello` нарушитель формирует дополнительные HELLO и TC
от каждого поддельного `OriginatorAddress`. Одновременно подделывается IPv4
source. Это принципиально: изменение только OriginatorAddress при одном
обычном IP-источнике не является полноценной проверкой множества соседей.
`SendSpoofedMessages` сериализует штатные OLSR-заголовки, UDP и IPv4 и отправляет
их через `Ipv4RawSocketFactory` на широковещательный адрес обычного интерфейса.
Реальный сетевой канал и неизменённый приёмник OLSR остаются в цепочке.
Поддерживается включённая проверка IPv4/UDP checksums.

HELLO содержит сведения о соседях нарушителя и максимальную готовность.
После двустороннего обмена штатный `ProcessHello` соседа принимает поддельные
личности как симметричных соседей. TC от этих личностей рекламирует связь
с реальным адресом нарушителя и заполняет Topology Set. MID, связывающий
поддельные адреса с главным адресом, не отправляется. `GetSybilPackets()`
считает пакеты, принятые raw-сокетом для отправки на каждом активном
интерфейсе. Исходящая передача видна в трассировках OLSR и IPv4. Успешное
появление ложных соседей проверяется по таблицам честного приёмника.

`ValidateSybilRange` проверяет весь диапазон перед выпуском поддельных
пакетов. Проверка отклоняет специальные диапазоны, совпадения с назначенными
адресами узлов и адреса известных подсетей или их broadcast. При нескольких
нарушителях каждому выделяют собственный диапазон. Модель реализует подделку
IPv4-источника в управляющих сообщениях. Оценка достижимости фиктивных адресов
потребует отдельной модели пересылки данных.

## Туннель

Файл: `ns3-49-olsr-wormhole.patch`.

| Параметр или метод | По умолчанию | Назначение |
|---|---|---|
| `WormholeEnabled` | `false` | Включить конец туннеля |
| `WormholeDelay` | `1 ms` | Задержка доставки по скрытому каналу, строго больше нуля |
| `SetWormholePeer(peer)` | peer отсутствует | Указать объект OLSR другого конца |

В сценарии необходимо включить оба конца и связать их двумя вызовами
`SetWormholePeer`. `RecvOlsr` перехватывает полученные HELLO/TC. `SendPacket`
берёт IPv4-адрес фактического исходящего интерфейса для собственной отправки.
При передаче одной копии через несколько интерфейсов кэш выбирает первое
успешное отправление. `TransferToWormhole` планирует доставку копии с заданной
задержкой через `Simulator::ScheduleWithContext` в контексте принимающего узла.
`ReplayWormhole` выпускает их на обычные интерфейсы второго конца через
`SendSpoofedMessages`, сохраняя исходный IPv4 source, OLSR originator, TTL
сообщения и hop count. HELLO, который в штатном протоколе не ретранслируется,
оказывается в удалённой компоненте; честные приёмники могут установить ложные
симметричные связи.

Для прекращения бесконечного отражения используются expiring-cache
`(originator, message sequence number)` и simulator-only `WormholeReplayTag`.
Tag — внутренняя метка пакета NS-3, не дополнительное поле сетевого протокола.
Она запрещает повторный захват уже выпущенной копии на другом конце.
`GetWormholeTransfers()` считает отправки через скрытый канал, а
`GetWormholeReplays()` — пакеты, принятые для отправки на активных интерфейсах
принимающего конца.

**Граница модели:** это управляющий туннель HELLO/TC по схеме курсовой.
Скрытый канал абстрактный: без модели полосы, очередей и потерь; его задержка
задаётся явно. Пакеты данных через скрытый канал не передаются. Ложная запись
соседства не означает наличия радиосвязи или успешной ARP-доставки данных.
Для исследования пропускной способности data-plane wormhole потребует
отдельного расширения. Текущая проверка доказывает перенос реальных сообщений
и изменение состояния честных узлов.

## Минимальные проверки

Сценарии находятся в `tests/olsr-*-check.cc`, копируются в `scratch/` выбранной
версии NS-3. Они используют `SimpleNetDevice` и `SimpleChannel` с явно
заблокированными несоседними связями: это детерминированные проверки
маршрутизации без модели Wi-Fi PHY и коллизий. Все checksums включены.

| Проверка | Топология | Что проверяется |
|---|---|---|
| Blackhole | Цепочка пяти узлов | Снижение доставки через средний узел, реальное подавление MPR-пересылки, сохранение локальной доставки нарушителю |
| Grayhole | Та же цепочка | Отключённая атака, p=0, p=0.5, p=1; отдельные счётчики данных и сообщений |
| Sybil | Два физических узла | Три поддельные личности приняты честным соседом как симметричные соседи |
| Wormhole | Две несвязанные пары | Через скрытый канал появляются симметричные соседи из другой компоненты; без атаки их нет |
| Pristine | Исходная цепочка | Доставка и fingerprint таблиц маршрутов совпадают с отключёнными blackhole/grayhole |

Результаты и журналы фактически выполненных проверок сохраняются в
`tests/results/olsr-summary.json` и `tests/results/olsr-*.log`.
Официальные тесты OLSR запускаются с отключёнными по умолчанию атаками.
Эти проверки не являются статистическим сравнением эффективности атак и
не заменяют Wi-Fi, мобильные и многократные эксперименты будущей главы 3.

### Фактически полученные результаты

Проверка проведена в WSL Ubuntu-26.04, g++ 15, NS-3.49. Для всех четырёх
патчей выполнены `patch --dry-run`, применение к чистым исходным файлам,
сборка соответствующего сценария и запуск с включённой и отключённой атакой.

| Запуск | Результат |
|---|---|
| Чёрная дыра выключена | Доставлены 300 из 300 пакетов транзитного потока и 300 из 300 пакетов, адресованных среднему узлу |
| Чёрная дыра включена | Доставлены 100 из 300 пакетов, отправленные до начала отбрасывания; локальная доставка 300 из 300; намеренно отброшены 52 транзитных пакета и 26 подходящих служебных сообщений |
| Серая дыра, p=0 | Доставка 300 из 300, намеренных потерь нет |
| Серая дыра, p=0.5 | Доставка 204 из 300; локальная доставка 300 из 300; намеренно отброшены 94 пакета и 11 сообщений |
| Серая дыра, p=1 | Доставка 100 из 300; локальная доставка 300 из 300; намеренно отброшены 41 пакет и 26 сообщений |
| Сивилла выключена / включена | У наблюдателя 0 / 3 поддельных симметричных соседа; размер Topology Set 0 / 3; при включении отправлены 165 пакетов поддельных личностей |
| Туннель выключен / включён | 0 / 1 удалённый симметричный сосед через физически несвязанные компоненты; число маршрутов 1 / 3; при включении 246 передач и 246 выпусков сообщений |

В чёрной и серой дырах отбрасывание начинается с 30-й секунды, поток идёт
с 20-й по 50-ю секунду. Подавление TC со временем удаляет часть маршрутов:
поэтому число недоставленных пакетов не равно счётчику намеренных потерь
на нарушителе. Для p=1 и чёрной дыры дополнительные RNG-потоки других узлов
могут изменить момент протокольных событий, но в контрольном запуске
доставлены одинаковые 100 пакетов до начала отбрасывания.

Повтор серой дыры с p=0.5, теми же seed/run и потоками дал полностью
совпадающие счётчики и fingerprint таблиц маршрутов. Для всех четырёх
отключённых модификаций fingerprint таблиц и наблюдаемые результаты
совпали с отдельной сборкой исходной библиотеки в той же топологии.

На каждом из четырёх вариантов пройдены штатные наборы `routing-olsr`,
`routing-olsr-header`, `routing-olsr-regression` и `olsr-traced-callback-typedef`.
В регрессии проверены HELLO, TC и bug 780. В тестах заголовков проверены
HNA, TC, HELLO, MID и кодирование времени EMF.

Дополнительные проверки подтвердили штатное автоматическое назначение RNG
при выключенной серой дыре, сохранение IPv4-источника и контекста принимающего
узла при туннелировании с дополнительным интерфейсом, принятие 1 и 64 адресов
Сивиллы при включённых и выключенных контрольных суммах и учёт отправок на
двух интерфейсах. Настройки с 65 личностями и недопустимым диапазоном
адресов приводят к ожидаемому отказу конфигурации.

## Пример запуска на Linux

В чистом корне NS-3.49:

```bash
patch --dry-run -p1 < /path/to/patches/ns3-49-olsr-blackhole.patch
patch -p1 < /path/to/patches/ns3-49-olsr-blackhole.patch
cp /path/to/patches/tests/olsr-blackhole-check.cc scratch/
./ns3 configure --enable-examples --enable-tests --enable-modules=olsr,applications
./ns3 build scratch/olsr-blackhole-check
./ns3 run 'olsr-blackhole-check --enabled=0'
./ns3 run 'olsr-blackhole-check --enabled=1'
```

Для остальных атак используются одноимённые patch и check. Перед сменой
атаки нужно взять другую чистую копию либо отменить прежний патч командой
`patch -R -p1 < прежний.patch`, предварительно проверив отсутствие собственных
изменений. Патчи не меняют систему и не предназначены для реальных устройств.

Дополнительные режимы контрольных сценариев запускаются из соответствующих
рабочих копий.

```bash
./ns3 run 'olsr-wormhole-check --enabled=1 --multiInterface=1'
./ns3 run 'olsr-sybil-check --identities=64 --checksums=0'
./ns3 run 'olsr-sybil-check --twoInterfaces=1'
```
