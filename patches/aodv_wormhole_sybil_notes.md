# Модели AODV wormhole и Sybil для NS-3.49

Патчи независимы: каждый накладывается на чистую NS-3.49 командой `patch -p1`. Их нельзя последовательно применять друг поверх друга. Оба изменяют только `src/aodv/model/aodv-routing-protocol.cc` и `.h`; штатное поведение сохраняется при выключенных атрибутах атаки.

## Туннель

`WormholeEnabled` по умолчанию `false`. `WormholeInterface` — номер существующего IPv4-интерфейса выделенного канала на каждом конце. При включении проверяется, что интерфейс существует и не является loopback. Номер берётся через `GetInterfaceForDevice`, а не задаётся по предположению.

Сценарий создаёт настоящий `PointToPointChannel` между удалёнными в основной топологии узлами. Через него передаются сериализованные сообщения AODV и реальные IP-пакеты данных. Это внеполосный канал модели, а не связь между живыми компьютерами.

Изменения кода:

- В `RecvRequest` при получении RREQ через интерфейс туннеля не выполняется обычное увеличение HopCount. Номер запроса и адрес источника сохраняются, поэтому продолжает работать штатный кэш дубликатов.
- В `RecvReply` аналогично скрывается увеличение HopCount у обычного RREP, пришедшего через туннель. HELLO не меняется.
- При отправке RREQ или пересылке RREP по интерфейсу туннеля сохраняется TTL служебного сообщения. Иначе длина обратного маршрута, заниженная туннелем, могла бы дать слишком короткий TTL ответа. На остальных интерфейсах сохраняется штатное уменьшение TTL.
- `WormholeControl` показывает тип сообщения, входной и сохранённый HopCount. Содержимое таблиц маршрутов не подставляется вручную.

Сценарий `aodv-wormhole-check.cc` рассматривает цепочку S–A, B–D и частный канал A–B. Есть три режима: `--mode=0` без частного канала, `--mode=1` с обычным каналом без сокрытия hop, `--mode=2` с туннелем. Проверяется фактический приём данных, передача по устройствам канала, срабатывание trace и число переходов в таблице источника: 3 для обычного канала и 2 для туннеля.

Ограничения: это модель дополнительного внеполосного канала с сокрытием одного логического перехода. Она не реализует IP-in-IP, общую L2-ретрансляцию радиокадров или безусловное сохранение TTL пакетов данных. У концов есть дополнительные IP-интерфейсы. Контрольный сценарий использует детерминированные point-to-point сегменты, чтобы отделить логику AODV от радиопотерь; он не является исследованием мобильной радиосети. Поэтому схема должна показывать выделенный канал и конкретную выбранную модель туннеля, а не обещать полностью невидимое объединение радиосегментов.

## Сивилла

`SybilEnabled` по умолчанию `false`; `SybilIdentityCount` задаёт от 1 до 256 дополнительных идентификаторов; `SybilFirstAddress` — первый адрес диапазона, по умолчанию `10.250.0.1`. Диапазон резервируется сценарием и не должен пересекаться с адресами честных узлов. Проверяются переполнение диапазона, multicast/зарезервированные старшие диапазоны, loopback и адреса самого атакующего узла. Модель требует включённого `EnableHello`.

В `SendHello` после настоящего HELLO создаётся серия дополнительных RREP с полями `destination = origin = fictitiousAddress`. Интервалы смещены на 1 мс между личностями. `SendSybilHello` повторно проверяет `SybilEnabled` в момент отправки и передаёт сериализованный пакет сокету узла. `SybilIdentityTx` фиксирует идентификатор после успешного вызова `SendTo`. Если атаку выключить во время симуляции, оставшиеся запланированные отправки пропускаются.

Сосед обрабатывает такие RREP штатной функцией `ProcessHello`, поскольку destination совпадает с origin, и создаёт отдельную действительную запись маршрута для каждого идентификатора. Проверочный сценарий читает таблицу именно соседнего узла и ищет точные destination со статусом UP; одной печати сообщений злоумышленником для успешной проверки недостаточно.

Ограничения: выбран HELLO-вариант загрязнения таблиц соседей и маршрутов. Он не подделывает одновременно RREQ, RERR и физический/MAC-адрес передатчика. UDP/IP-адрес действительного отправителя остаётся наблюдаемым, а поддельные адреса не становятся реально достижимыми конечными устройствами. Это существенно для защиты работы: создание фиктивной записи не доказывает доставку данных фиктивному узлу. Нельзя описывать этот патч как полную эмуляцию независимых радиоустройств.

## Воспроизведение

В соответствующее чистое дерево применить один патч, скопировать его `.cc` сценарий в `scratch/`, настроить `./ns3 configure --enable-examples --enable-tests --enable-modules=aodv,applications,point-to-point --disable-python-bindings`, затем собрать соответствующий target. Для Sybil достаточно тех же модулей.

Туннель: `./ns3 run "aodv-wormhole-check --mode=0"`, затем режимы 1 и 2.

Сивилла проверяется командами `./ns3 run "aodv-sybil-check --attack=0"` и `./ns3 run "aodv-sybil-check --attack=1 --count=3"`. Другие размеры группы задаются через `--count`. Команда `./ns3 run "aodv-sybil-check --attack=1 --count=3 --disableAfterFirst=1"` выключает атаку сразу после первой отправки и проверяет число принятых личностей.

Итоги выполненных запусков сохраняются отдельно в `tests/results/` с префиксами `aodv-wormhole` и `aodv-sybil`. Приведённые сценарии проверяют работоспособность конкретной модели; они не заменяют количественные эксперименты третьей главы.

## Выполненные проверки

На локальной Ubuntu-26.04 в WSL собраны оба независимых варианта. Проверка наложения каждого патча на исходную NS-3.49 прошла без ошибок. Для каждого варианта также прошли штатные наборы `aodv-routing-id-cache`, `routing-aodv`, `routing-aodv-loopback`, `routing-aodv-regression`.

| Модель | Режим | Наблюдение |
|---|---|---|
| Wormhole | Без частного канала | 0 принятых байт, маршрута нет |
| Wormhole | Обычный частный канал | 6400 байт, 3 объявленных перехода, 0 скрытых control-hop |
| Wormhole | Скрытый переход туннеля | 6400 байт, 2 объявленных перехода, 5 событий скрытия control-hop, 58 передач на устройствах туннеля |
| Sybil | Выключена | 0 фиктивных записей у соседа, 0 дополнительных передач |
| Sybil | 1 личность | 1 действительная запись у соседа, 4 успешных вызова `SendTo` |
| Sybil | 3 личности | 3 действительные записи у соседа, 12 успешных вызовов `SendTo` |
| Sybil | 10 личностей | 10 действительных записей у соседа, 40 успешных вызовов `SendTo` |
| Sybil | 256 личностей | 256 действительных записей у соседа, 1024 успешных вызова `SendTo` |
| Sybil | Выключение после первой отправки из 3 | 1 успешный вызов `SendTo` и 1 действительная запись у соседа |

Туннель после возврата дерева сборки к финальному патчу повторно дал те же показатели режима 2. При проверке Sybil исходники двух файлов временно заменялись в том же дереве сборки; это сокращает время сборки, но каждый проверенный вариант получен независимо от чистой базы. Логи в `tests/results/` фиксируют команды сборки, состояние таблиц и результаты утверждений сценариев.
