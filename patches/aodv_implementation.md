# Реализация атак AODV для NS-3.49

Патчи предназначены для самостоятельных учебных экспериментов внутри NS-3.49. Каждый патч применяется отдельно к чистому дереву версии 3.49. Последовательное наложение четырёх патчей не предусмотрено. Штатные файлы протокола и заголовки сообщений сохранены; новый формат пакетов не вводится.

## Чёрная дыра

Файлы: `src/aodv/model/aodv-routing-protocol.h` и `.cc`.

* Атрибут `IsMalicious` (по умолчанию false) включает атаку на конкретном экземпляре `aodv::RoutingProtocol`.
* Атрибут `AttackSequenceBoost` (100, допустимо от 1 до 2^31-1) задаёт прибавку к номеру последовательности ложного ответа. Используется 32-битная последовательностная арифметика; огромный числовой максимум не объявляется универсально самым свежим номером.
* В `RecvRequest` сохранены проверки повторов, чёрного списка и создание обратного маршрута. Запрос к самому узлу обрабатывается штатно. Для чужого адресата вызывается `SendAttackReply`: RREP заявляет один переход до адресата и более свежий номер последовательности. Ответ отправляется по существующему обратному маршруту. После ответа данный RREQ дальше не распространяется через злоумышленника.
* Ложная локальная запись с nextHop, равным удалённому недостижимому адресату, не создаётся. Ложная информация распространяется в RREP и попадает в таблицы получающих его честных узлов. Именно эти таблицы должны быть загрязнены для привлечения трафика.
* В `RouteInput` добавлена ветка после штатной обработки локального и широковещательного трафика и проверки разрешения IP-пересылки. Транзитный одноадресный пакет уничтожается; возвращается true, поскольку пакет обработан этим протоколом. Возврат false из старого патча NS-3.25 позволял бы `Ipv4ListRouting` пробовать следующий протокол и некорректно описывал намеренный приём пакета злоумышленником.
* `AttackDrop` сообщает о намеренно отброшенном пакете, `ForgedReply` — об отправленном ложном RREP. Ошибка отсутствующего маршрута/ICMP не генерируется: это скрытое злонамеренное отбрасывание. Эти отбрасывания следует считать по новому источнику трассировки, а не по обычному IP Drop.

Атака не отбрасывает пакеты, адресованные самому злоумышленнику, его собственные пакеты и штатный широковещательный обмен AODV. Отсутствие гарантии выбора маршрута во всех топологиях является свойством модели: расположение узлов, потери канала и другие ответы продолжают иметь значение.

## Серая дыра

Независимый патч включает ту же отправку ложного RREP и атрибут `AttackDropProbability` (0.5, диапазон [0,1]). Каждый транзитный одноадресный пакет отбрасывается независимо с этой вероятностью. При p=0 отбрасываний нет; при p=1 отбрасываются все такие пакеты. Это эквивалентность по пересылке данных, а не побайтовая эквивалентность всего служебного обмена двух патчей.

Принципиальное исправление схемы из раздела 2.2: серая дыра после ложного ответа **продолжает штатную обработку/распространение RREQ**, чтобы выяснить настоящий дальнейший путь. В противном случае без предварительно известного маршрута пакеты из доли 1-p тоже терялись бы, и модель фактически становилась бы чёрной дырой независимо от параметра p. Штатный RREP от настоящего получателя создаёт у злоумышленника маршрут, которым могут воспользоваться неотброшенные пакеты. Пока этот путь ещё не обнаружен, возможны обычные потери начального переходного периода; вероятность p относится к решениям злонамеренного отбрасывания, а не ко всем потерям приложения.

При выключенной атаке сохраняется один штатный поток случайности. Для включённой атаки `AssignStreams` назначает два потока и создаёт `UniformRandomVariable` отбрасывания сразу с явным номером, сохраняя порядок автоматических потоков. При автоматическом назначении генератор атаки создаётся при первой проверке с дробной вероятностью. Решения при `p = 0` и `p = 1` не требуют случайной выборки. Роль `IsMalicious` задаётся до явного назначения потоков. В контрольном сценарии каждому узлу выделены индексы `100 + 10*i`, а Wi-Fi использует индексы начиная с 1000.

## Соответствие исходным схемам

Сохранены привлечение трафика ложным RREP, завышение номера последовательности и отбрасывание транзитных данных. Два элемента требуют обновления рисунков/описания:

1. «Ложная запись в таблице маршрутов» на локальном узле заменяется формированием ложного RREP; ложная запись возникает у получателей ответа. Рабочую локальную таблицу маршрутов не следует делать заведомо непригодной для пересылки.
2. Для серой дыры нельзя перечёркивать все выходы RREQ без оговорки о предварительно найденном пути. В представленной модели RREQ сохраняется; прямой маршрут строится штатно.

## Минимальная проверка blackhole и grayhole

Сценарий `tests/aodv-drop-check.cc` строит цепочку из четырёх неподвижных Wi-Fi узлов с радиусом 75 м и расстоянием между соседями 60 м. Узел 0 отправляет 300 UDP-пакетов узлу 3 через узлы 1 и 2. Злоумышленник — узел 1. Отдельные 10 пакетов адресованы самому узлу 1, чтобы проверить сохранение локальной доставки.

Сценарий проверяет отключённую атаку, наличие ложных RREP, злонамеренные отбрасывания, поступление/отсутствие пакетов у получателя и сохранение локальной доставки. Для серой дыры предусмотрены p=0, p=0.5, p=1; при p=0.5 проверяется грубое соответствие доли решений заданной вероятности (допуск 0.15 для короткой проверки, не статистическое исследование). JSON включает seed, run и отпечаток UID отброшенных пакетов для сравнения повторных запусков.

Применение из корня чистого NS-3.49 (путь к каталогу проекта заменить своим):

```bash
patch --dry-run -p1 < /path/to/patches/ns3-49-aodv-blackhole.patch
patch -p1 < /path/to/patches/ns3-49-aodv-blackhole.patch
cp /path/to/patches/tests/aodv-drop-check.cc scratch/
./ns3 configure --enable-examples --enable-tests --enable-modules=aodv,wifi,mobility,applications --disable-python-bindings
./ns3 build aodv-drop-check -j 3
./ns3 run 'aodv-drop-check --checkAutomaticStreams=1'
./ns3 run 'aodv-drop-check --malicious=0'
./ns3 run 'aodv-drop-check --malicious=1'
```

Для grayhole нужна отдельная чистая копия (либо сначала обратное применение blackhole через `patch -R -p1`), затем независимый grayhole-патч. Команды сценария:

```bash
./ns3 run 'aodv-drop-check --checkAutomaticStreams=1'
./ns3 run 'aodv-drop-check --malicious=0'
./ns3 run 'aodv-drop-check --malicious=1 --probability=0'
./ns3 run 'aodv-drop-check --malicious=1 --probability=0.5 --seed=17 --run=1'
./ns3 run 'aodv-drop-check --malicious=1 --probability=0.5 --seed=17 --run=1'
./ns3 run 'aodv-drop-check --malicious=1 --probability=1'
```

В [режиме с задержкой](README.md#серая-дыра-с-отбрасыванием-посреди-потока)
ложные RREP разрешены с начала запуска. До 6-й секунды вероятность отбрасывания
равна нулю, затем сценарий устанавливает значение `--probability`.
При `p = 1` в выполненном прогоне доставлено 99 пакетов до переключения и 0 после.

Два запуска с одинаковыми параметрами должны дать одинаковый JSON; изменение run задаёт другую реализацию случайного процесса. Одна короткая цепочка подтверждает работу механизмов, но не доказывает влияние атаки на произвольную мобильную сеть.

## Источники и версия

Реализация сверена с фактическими исходниками локального NS-3.49: `src/aodv/model/aodv-routing-protocol.{cc,h}`, `src/aodv/helper/aodv-helper.cc`, `src/aodv/doc/aodv.rst`, а также со схемами проекта. Структура протокола: `RouteInput` — локальная доставка/транзит, `RecvRequest` — запросы маршрута, `SendReply`/`RecvReply` — ответы, `AssignStreams` — явное назначение случайных потоков.

Официальные исходники версии: <https://gitlab.com/nsnam/ns-3-dev/-/tree/ns-3.49/src/aodv>.
Стандарт AODV: <https://www.rfc-editor.org/rfc/rfc3561>.

## Выполненные проверки blackhole и grayhole

Проверки выполнены в WSL Ubuntu-26.04, компилятор GCC 15.2.0, NS-3.49 из локального чистого дерева. Включены examples и tests; собраны затронутый модуль, контрольный сценарий и штатная библиотека тестов AODV. Полная сборка всех примеров других модулей не заявляется.

| Патч и режим | Отправлено | Доставлено | AttackDrop | ForgedReply | Локально узлу 1 |
|---|---:|---:|---:|---:|---:|
| Blackhole выключен | 300 | 300 | 0 | 0 | 10/10 |
| Blackhole включён | 300 | 0 | 300 | 1 | 10/10 |
| Grayhole выключен | 300 | 300 | 0 | 0 | 10/10 |
| Grayhole p=0 | 300 | 299 | 0 | 2 | 10/10 |
| Grayhole p=0.5, run=1 | 300 | 151 | 148 | 2 | 10/10 |
| Grayhole p=0.5, run=2 | 300 | 156 | 143 | 2 | 10/10 |
| Grayhole p=1 | 300 | 0 | 300 | 1 | 10/10 |

Единственная дополнительная потеря в промежуточных вариантах grayhole подтверждена штатной трассировкой IP: ordinaryIpDrops=1, ordinaryDropReason=2 (DROP_NO_ROUTE) на узле-злоумышленнике. Она относится к начальному периоду поиска настоящего дальнейшего маршрута и не засчитывается как злонамеренный AttackDrop. Повтор p=0.5 с seed=17 и run=1 дал идентичный JSON и отпечаток UID отброшенных пакетов (`cmp` завершился успешно). Это проверка воспроизводимости выбранного сценария, а не обобщённая статистика атаки.

Проверка `--checkAutomaticStreams=1` подтвердила один автоматически выделенный поток у выключенной атаки, как в чистом AODV. При включённой серой дыре явное назначение использует два заданных потока и не расходует автоматические. Журналы записаны в `tests/results/aodv-blackhole-automatic-streams.log` и `aodv-grayhole-automatic-streams.log`.

Для обоих патчей прошли четыре неизменённых набора NS-3: `aodv-routing-id-cache`, `routing-aodv`, `routing-aodv-loopback`, `routing-aodv-regression` (включая эталонные PCAP chain и bug-772). Скрипт `tests/run_aodv_unit_tests.sh` собирает библиотеку `aodv-test`, компилирует стандартный `utils/test-runner.cc` с этой библиотекой и запускает перечисленные наборы; исходники тестов не изменяются.

Проверки наложения на исходное дерево записаны в `tests/results/aodv-blackhole-dry-run.log` и `aodv-grayhole-dry-run.log`. SHA-256 исходных файлов до модификации сохранены в `tests/results/aodv-base-sha256.txt`. Результаты сценариев и штатных тестов приведены в [сводке AODV](tests/results/aodv-validation-summary.json).

Описание двух оставшихся моделей AODV и их проверок: [туннель и Сивилла](aodv_wormhole_sybil_notes.md).
